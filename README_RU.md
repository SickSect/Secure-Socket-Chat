# Secure Chat

TCP-чат со сквозным шифрованием, написанный на Java с нуля. Акцент на понимании
криптографических примитивов, а не на использовании высокоуровневых библиотек.

Текущий релиз (**v0.7**) добавляет к ядру E2E-шифрования **пер-месседжный
forward secrecy**: протокол сообщений v3 с односторонними HMAC-цепочками и
DH-ротацией. Ранее релиз усилил защиту развёртывания: TLS 1.3 для всего
трафика, handshake с привязкой к транскрипту и явным подтверждением ключей,
строгие порядковые номера сообщений, JWT-аутентификация доступа к чату,
пользователи в PostgreSQL и конфигурация, которая по умолчанию всё запрещает.

## Возможности

- **Сквозное шифрование (E2E)** — содержимое сообщений шифруется
  направленными ключами AES-256-GCM. Сервер только маршрутизирует шифртекст и не
  может прочитать сообщения.
- **Forward secrecy на сессию** — ключи сессии выводятся из эфемерных ECDH-пар
  (P-256), которые уничтожаются после handshake.
- **Пер-месседжный forward secrecy** — каждое сообщение шифруется свежим
  ключом из односторонней HMAC-цепочки: утечка одного ключа открывает ровно
  одно сообщение. DH-ротация пересчитывает корень каждый раунд обмена, поэтому
  даже украв состояние сессии, атакующий не откроет сообщения после следующей
  ротации (break-in recovery).
- **Привязка ключей к транскрипту** — HKDF-SHA256 использует в качестве соли
  полный транскрипт handshake (обе идентичности и оба эфемерных ключа), поэтому
  ключи нельзя переиспользовать между собеседниками или сессиями.
- **Явное подтверждение ключей** — обе стороны доказывают, что вывели одинаковые
  ключи, прежде чем сессия станет доступной.
- **Защита от replay и переупорядочивания** — каждое E2E-сообщение несёт
  монотонный порядковый номер, аутентифицированный через GCM AAD.
- **Аутентифицированный handshake** — эфемерные ключи подписываются
  долгоживущим RSA-2048 ключом; подпись привязана к роли и обоим именам.
- **Проверка identity-ключей** — первый ключ собеседника закрепляется локально
  (TOFU), а при его смене клиент блокирует handshake до явного `/trust`.
  Команда `/safety <user>` показывает safety number для сверки по другому
  каналу связи — это защита от подмены ключа сервером.
- **Персистентная личность** — у каждого пользователя есть долгоживущая
  RSA-пара, хранящаяся локально в файле под защитой пароля
  (PBKDF2 600k + AES-GCM).
- **Транспорт TLS 1.3** — и REST (HTTPS), и TCP-порт чата используют TLS 1.3;
  старый статический PSK удалён.
- **JWT-аутентификация** — регистрация и вход через REST; идентичность в чате
  берётся из проверенного токена, а не из данных клиента.
- **Отзыв сессий** — короткие access-токены (10 минут) плюс одноразовые
  refresh-токены с ротацией и обнаружением повторного использования;
  `/logout` немедленно отозвывает **все** выданные токены пользователя
  (`token_version`), включая вход в чат.
- **Жизненный цикл сессии** — сессии истекают по idle-таймауту или абсолютному
  возрасту, после чего следующий запрос запускает новый handshake (ротацию
  ключей).
- **Обнуление ключей** — ключи сессии и теги подтверждения затираются при
  истечении, отключении или выходе (best effort в JVM).
- **Безопасные значения по умолчанию** — default-deny для HTTP-авторизации,
  ограниченные кадры и пулы потоков, rate limiting, проверка RSA/EC-ключей,
  отсутствие stack trace в ответах.

## Технологии

- **Java 23**
- **Spring Boot** — REST endpoints, dependency injection, конфигурация
- **Spring Security** — BCrypt для паролей, default-deny filter chain
- **PostgreSQL** + **Flyway** — пользователи и миграции схемы
- **JJWT** — выпуск и проверка JSON Web Token
- **Gradle** — сборка
- **TestNG** — тестирование
- **TLS 1.3** — HTTPS REST API и транспорт чата
- Сырые TCP-сокеты для транспорта чата (намеренно без WebSocket/STOMP — чтобы
  работать с протоколом напрямую)

## Быстрый старт

### Требования

- JDK 23+
- PostgreSQL 16+ (база `secure_chat`)

### 1. Настройте окружение

```powershell
Copy-Item .env.example .env
```

Отредактируйте `.env` и задайте как минимум:

- `DB_PASSWORD` — пароль PostgreSQL
- `JWT_SECRET` — случайное значение не короче 32 байт (оставляйте пустым только
  для одноразового локального запуска: тогда токены сбрасываются при рестарте)
- `JWT_EXPIRATION_MINUTES` — TTL access-токена (по умолчанию 10 минут);
  долгие сессии живут за счёт refresh-токенов `REFRESH_TOKEN_DAYS`
  (по умолчанию 30 дней, одноразовых — с ротацией при каждом `/refresh`)
- `TLS_KEYSTORE_PASSWORD` / `TLS_KEY_PASSWORD` / `TLS_TRUSTSTORE_PASSWORD`

Gradle автоматически загружает `.env` для `bootRun`, `runServer`, `runClient` и
`test`. Сам Spring Boot не читает `.env`; если запускаете JAR напрямую,
экспортируйте переменные в shell или IDE.

### 2. Сгенерируйте сертификаты для разработки

```powershell
powershell -ExecutionPolicy Bypass -File certs/generate-dev-certs.ps1
```

Скрипт создаёт `certs/server-keystore.p12`, `certs/server.crt` и
`certs/client-truststore.p12` (все игнорируются git). Подробности —
[`certs/README.md`](certs/README.md).

### 3. Создайте базу данных

```bash
createdb -U postgres secure_chat
```

### 4. Запустите сервер

```powershell
.\gradlew.bat bootRun
```

При старте приложение:

1. Применяет миграции Flyway (таблица пользователей)
2. Запускает HTTPS REST-сервер на порту `8443`
3. Запускает TLS-сервер чата на порту `5000`

### 5. Запустите клиент

Клиент — отдельное консольное приложение. Запускайте из IDE
(`org.ugina.client.ChatClient`) — включите **Allow multiple instances** в
конфигурации запуска, чтобы открыть несколько клиентов. Он читает
`CHAT_HOST`, `CHAT_TLS_PORT`, `AUTH_URL` и переменные `TLS_TRUSTSTORE*` из
окружения.

> Запуск клиента через `./gradlew runClient` **не рекомендуется** — Gradle
> перехватывает stdin и ломает интерактивный ввод. Используйте конфигурацию
> запуска в IDE.

### Типичный сценарий

1. Запустите сервер.
2. Запустите два экземпляра клиента.
3. В каждом: зарегистрируйте имя/пароль (пароль ≥ 8 символов), затем войдите.
4. Отправьте сообщение через `@username текст` — первое сообщение запускает
   E2E-handshake, последующие используют уже выведенные ключи.
5. Для защиты от подмены ключа сервером выполните `/safety <username>` у обоих
   собеседников и сравните числа по другому каналу (лично, по телефону,
   в подписанном сообщении).

### Проверка ключей

При первом контакте клиент запоминает fingerprint публичного ключа собеседника
в `~/.secure-chat/known-peers.tsv`. Если сервер позже вернёт другой ключ, клиент
откажется его использовать и покажет предупреждение с ожидаемым и полученным
fingerprint. После сверки нового ключа по другому каналу его можно принять:

```text
/safety <user>                       # safety number для сверки
/fingerprint                         # ваш fingerprint
/trust <user> <fingerprint-prefix>   # принять новый ключ, минимум 16 hex-символов
```

Это Trust On First Use (TOFU): первый контакт всё ещё доверяет серверу, поэтому
safety number нужно сравнивать именно при первом знакомстве. Полное устранение
этого риска требует key transparency — см. [`SECURITY.md`](SECURITY.md).

## Обзор архитектуры

Система использует следующие типы ключей, у каждого одна ответственность:

| Ключ | Алгоритм | Область | Назначение |
|------|----------|---------|------------|
| Identity-ключ | RSA-2048 | На пользователя, долгоживущий | Подписывает эфемерные ключи в handshake |
| Эфемерный ключ | ECDH P-256 | На сессию | Выводит общий секрет, затем уничтожается |
| Ключи сессии | AES-256-GCM | На сессию, на направление | Шифруют содержимое сообщений (E2E) |
| TLS-сертификат | X.509 / TLS 1.3 | На сервер | Защищает транспорт клиент-сервер |

Сообщение шифруется один раз ключом E2E-сессии. TLS защищает этот шифртекст
(и метаданные маршрутизации) при передаче. Сервер видит метаданные, но не
содержимое; сетевой наблюдатель не видит ни того, ни другого.

Аутентификация абстрагирована интерфейсом `AuthProvider`. Текущая реализация —
локальная (BCrypt + JWT), но абстракция позволяет подключить внешний провайдер
(например, Keycloak), не трогая слой чата.

Полная последовательность handshake и форматы сообщений — в
[`protocol/RU/PROTOCOL_07.md`](protocol/RU/PROTOCOL_07.md). Модель угроз и
остаточные риски — в [`SECURITY.md`](SECURITY.md).

## Дорожная карта

### v0.1–v0.3 — готово
- Базовый TCP-чат с несколькими клиентами
- Шифрование транспорта
- Сквозное шифрование через гибридную схему RSA + AES
- Защита от replay-атак (timestamp + nonce)

### v0.4 — готово
- Forward secrecy через эфемерные ECDH-ключи
- Персистентные RSA identity-ключи под защитой пароля
- Аутентифицированный handshake (эфемерные ключи подписаны identity-ключом)
- Вывод ключей сессии через HKDF

### v0.5 — готово
- Регистрация и вход пользователей (REST API)
- Аутентификация на основе JWT
- Персистентность в PostgreSQL с миграциями Flyway
- Жизненный цикл сессии (idle + absolute timeout, ротация ключей)

### v0.6 — готово
- TLS 1.3 вместо статического PSK на транспорте
- Handshake v2: HKDF с привязкой к транскрипту, направленные ключи, явное
  подтверждение
- Строгие порядковые номера сообщений (защита от replay/переупорядочивания)
- Default-deny HTTP-авторизация и ужесточённая конфигурация
- Rate limiting, ограниченные кадры и пулы потоков
- Проверка ключей: TOFU-закрепление, safety numbers, `/trust`
- Инструменты для локальных сертификатов и `SECURITY.md`

### v0.7 — в работе
- **Per-message forward secrecy (Double Ratchet) — готово**: протокол E2E v3,
  HMAC-цепочки + DH-ротация, `RatchetTest`
- **Refresh-токены и отзыв токенов — готово**: ротация, reuse detection,
  `token_version`, `/refresh`, `/logout`, `AUTH_FLOW_OK`
- **Ротация identity-ключа — готово**: `/rotate-key` (step-up: сессия + пароль),
  самопочинка верификации при смене ключа, `KEY_ROTATE_E2E_OK`
- Key transparency (append-only log) для проверки ключей без ручного сравнения

### v1.0 — планируется
- Транспорт WebSocket + веб-клиент
- Поддержка нескольких устройств (ключи на устройство)
- Персистентная история сообщений и доставка офлайн

## Замечания по безопасности

Это учебный проект. Он реализует настоящие криптографические конструкции и
покрыт unit-тестами, но **не проходил аудит** и не должен использоваться для
защиты чувствительной переписки. Известные ограничения — доверие к серверу при
**первом** получении ключа (TOFU), отсутствие key transparency, per-message
forward secrecy и best-effort затирание памяти — перечислены в
[`SECURITY.md`](SECURITY.md).
