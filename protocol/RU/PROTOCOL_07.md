# Secure Chat — спецификация протокола v3 (v0.7)

Статус: актуально для релиза **v0.7**.
Предыдущие версии: [`PROTOCOL_06.md`](PROTOCOL_06.md) (v2), [`PROTOCOL_05.md`](PROTOCOL_05.md).

> **Совместимость:** протокол E2E v3 **несовместим** с клиентами v0.6:
> старый клиент отклоняет кадр с `ver = 3`, новый — кадр с `ver = 2`
> (`Unsupported E2E payload version`). Обновлять обе стороны.

---

## 1. Обзор

Secure Chat состоит из двух независимых каналов:

1. **REST API по HTTPS** — регистрация и вход, выдача JWT.
2. **TCP-чат по TLS 1.3** — JOIN, handshake, обмен сообщениями.

Содержимое сообщений дополнительно шифруется сквозным образом (E2E) на
клиентах. Сервер видит только метаданные и непрозрачный `e2ePayload`.

Что изменилось в v3 по сравнению с v2:

| v2 | v3 |
|----|----|
| Два направляющих AES-ключа на всю сессию | **Ключ на каждое сообщение** из односторонней HMAC-цепочки |
| Нет ротации ключей внутри сессии | **DH-ротация** раз в ход: новый корень + новые цепочки |
| Kадр `[ver][seq][IV][CT]` | `[ver][flags][ratchetPub?][seq][chainIdx][IV][CT]` |
| AAD: имена + sequence | AAD: флаг + ratchet-ключ + имена + sequence + chainIndex |
| Forward secrecy только на уровне сессии | Per-message FS + break-in recovery |
| Эфемерные ключи уничтожались после handshake | Эфемерные ключи handshake становятся **начальной парой ратчета** |

Не изменилось: транспорт, кадрирование, REST-аутентификация, набор команд,
handshake-сообщения (`INIT_SESSION`/`SESSION_ACK`/`SESSION_CONFIRM`),
подписи RSA, таймауты, коды ошибок.

---

## 2. Транспорт и кадрирование

- REST: HTTPS, только TLS 1.3, порт по умолчанию `8443`.
- Чат: TLS 1.3, порт по умолчанию `5000`.
- Кадр — одна строка UTF-8, завершённая `\n`. `\r` игнорируется.
- Максимальная длина кадра — **96 KiB** (96 × 1024 символов) на клиенте и на
  сервере. Превышение закрывает соединение.
- JSON кодируется Jackson. Неизвестные поля игнорируются.
- Клиент проверяет имя хоста TLS
  (`endpointIdentificationAlgorithm=HTTPS`) и использует отдельный truststore
  (`TLS_TRUSTSTORE`).

## 3. Аутентификация (REST)

Изменения в v0.7: пароль по-прежнему даёт **пару токенов** — короткий
access JWT + одноразовый refresh token; добавлены `/refresh` и `/logout`.

### POST /api/auth/register

Без изменений относительно v2 — см.
[`PROTOCOL_06.md`, раздел 3](PROTOCOL_06.md#3-аутентификация-rest)
(request `username/password/publicKey`, ответ `201`, ошибки `400/409/429`).

### POST /api/auth/login

Request — без изменений. Ответ `200 OK`:

```json
{
  "token": "<access JWT>",
  "expiresAt": 1760000000000,
  "refreshToken": "<43 символа base64url>",
  "refreshExpiresAt": 1762592000000
}
```

Ошибки: `401` (`AUTHENTICATION_FAILED`), `429` (`RATE_LIMIT_EXCEEDED`).

### POST /api/auth/refresh

Обмен одноразового refresh token на новую пару (ротация):

```json
{ "refreshToken": "vnk1Jm4ZpOBK4xy6..." }
```

Ответ `200 OK` — та же форма, что у login (новая пара). Ошибки:

- `401 INVALID_TOKEN` — токен неизвестен, просрочен **или уже использован**;
  предъявление уже использованного/отозванного токена трактуется как кража
  и **отзывает всю семью** токенов этого логина (reuse detection);
- `400 VALIDATION_FAILED` — пустое поле;
- `429 RATE_LIMIT_EXCEEDED` — лимит30/час на IP (общий с `/logout`).

### POST /api/auth/logout

```json
{ "refreshToken": "vnk1Jm4ZpOBK4xy6..." }
```

Ответ `200 OK`:

```json
{ "status": "logged_out" }
```

Действие: отзыв **всей семьи** refresh-токенов + `users.token_version += 1`,
что немедленно убивает **все** выданные access JWT (включая `JOIN` в чат).
Идемпотентно: неизвестный токен тоже даёт `200` (не создаём оракула
валидности). `429` — общий лимит с `/refresh`.

### POST /api/auth/rotate-key

Ротация публичного identity-ключа (step-up: **живая сессия + пароль**):

```json
{ "password": "...", "publicKey": "<Base64 RSA ≥ 2048>" }
```

Заголовок: `Authorization: Bearer <access JWT>` — обязателен: из токена
берётся владелец, проверяются подпись, срок и `ver`.

Ответ `200 OK`:

```json
{ "status": "key_rotated", "username": "alice" }
```

Ошибки:

- `401 INVALID_TOKEN` — Bearer-токен отсутствует, мусорный или отозванный;
- `401 AUTHENTICATION_FAILED` — неверный пароль (общий rate-limit bucket с
  `/login`: 10/час на IP — единый бюджет на подбор пароля);
- `409 REGISTRATION_FAILED` — ключ некорректен (меньше 2048 бит, плохой
  exponent, неверный формат);
- `400 VALIDATION_FAILED` — пустые поля.

Приватная часть ключа генерируется **на клиенте** и серверу не передаётся
(иначе E2E было бы бессмысленно). После ротации следующий `GET_KEY`
возвращает новый ключ: у каждого пира срабатывает проверка TOFU
(«ключ изменился» → блокировка до `/trust`), а клиент с закешированным
старым ключом повторяет проверку подписи со свежеполученным ключом
(`ChatClientCore.verifyPeerSignature`), чтобы пользователь увидел явный
флоу смены ключа, а не `BAD_SIGNATURE`.

### Access JWT

- алгоритм HS256, issuer `secure-chat`, `sub` = username;
- claims: `jti` (UUID — каждый токен уникален даже в пределах одной секунды),
  `iat`, `exp` (`JWT_EXPIRATION_MINUTES`, по умолчанию **10 минут**),
  `ver` = `users.token_version`;
- проверка: подпись + issuer + срок + `sub`; дополнительно `ver` сверяется с
  БД при **каждом** использовании (в т.ч. при `JOIN` в чат) — несовпадение →
  `INVALID_TOKEN`. Повышение `token_version` = мгновенный отзыв всех токенов.

### Refresh token

- 32 случайных байта → base64url (43 символа), срок `REFRESH_TOKEN_DAYS`
  (по умолчанию30 дней);
- в БД хранится **только** `token_hash = HMAC-SHA256(JWT_SECRET, token)`
  (утечка БД не даёт живых токенов, без `JWT_SECRET` нельзя проверить даже
  предположение);
- все токены одного логина принадлежат `family_id` (UUID семьи);
- одноразовый: при каждом `/refresh` строка помечается `rotated_at` и
  создаётся новая строка той же семьи;
- отзыв: по `/logout` (семья целиком) или при reuse detection (семья целиком).

Схема таблицы — миграция `V3__token_revocation.sql`:
`refresh_tokens(id, token_hash UNIQUE, family_id, user_id FK, expires_at,
created_at, rotated_at, revoked_at)` + `users.token_version`.

## 6. Handshake v3

Обозначения:

- `A` — инициатор, `B` — ответчик.
- `ID_A`, `ID_B` — имена пользователей.
- `(E_A, e_A)`, `(E_B, e_B)` — эфемерные пары P-256 handshake; они же —
  **начальная пара ратчета** каждой стороны.
- `K` — общий секрет ECDH.
- `H` — SHA-256 транскрипта.
- `root` — общий корень ратчета.

### 6.1. Каноническая подпись

Перед подписью строится длина-префиксная строка:

```
LABEL = "secure-chat/v3/handshake"
payload = len(LABEL)||LABEL || len(role)||role || len(signer)||signer ||
          len(peer)||peer || len(ephemeralPub)||ephemeralPub
```

`len(x)` — 4 байта big-endian. Все строки — UTF-8.

- Инициатор подписывает `role = "init"`, `signer = ID_A`, `peer = ID_B`,
  `ephemeralPub = E_A`.
- Ответчик подписывает `role = "ack"`, `signer = ID_B`, `peer = ID_A`,
  `ephemeralPub = E_B`.

Подпись — `SHA256withRSA` ключом identity. Привязка роли и обоих имён не даёт
переиграть захваченный INIT другому собеседнику или в обратном направлении.

### 6.2. Транскрипт и вывод корня

```
transcript = len("secure-chat/v3/transcript") ||
             len(ID_A) || len(ID_B) || len(E_A) || len(E_B)

H = SHA-256(transcript)
```

HKDF-SHA256 (`HkdfCrypto.derive`):

```
root              = HKDF(K, salt = H, info = "secure-chat/v3/root",              32)
initiator-confirm = HKDF(K, salt = H, info = "secure-chat/v3/initiator-confirm", 32)
responder-confirm = HKDF(K, salt = H, info = "secure-chat/v3/responder-confirm", 32)
```

Подтверждения (`conf_A`, `conf_B`) сравниваются в постоянном времени
(`MessageDigest.isEqual`), как и в v2.

### 6.3. Первые цепочки ратчета

Направления: `i2r` — инициатор → ответчик, `r2i` — ответчик → инициатор.

DHKDF-шаг (`SessionCrypto.kdfRk`):

```
prk     = HMAC-SHA256(key = root, message = dhSecret)
newRoot = HMAC-SHA256(key = prk, message = "secure-chat/v3/ratchet/<dir>/root")
chain   = HMAC-SHA256(key = prk, message = "secure-chat/v3/ratchet/<dir>/chain")
```

Инициатор при **первой отправке** (лениво, `SessionContext.beginSend`):

```
(root, CK_i2r) = kdfRk(root, DH(e_A, E_B), dir = "i2r")
```

Ответчик при **получении первого сообщения** (`SessionContext.planReceive`):

```
шаг 1: (root, CK_i2r) = kdfRk(root, DH(e_B, E_A), dir = "i2r")   ← то же самое, что у A
шаг 2: (E_B2, e_B2)   = новая пара P-256
       (root, CK_r2i) = kdfRk(root, DH(e_B2, E_A), dir = "r2i")
```

`DH(e_A, E_B) == DH(e_B, E_A)`, `dir` совпадает с направлением цепочки —
поэтому обе стороны получают **одинаковые** `root` и `CK_i2r`. Дальше ротация
идёт строго по очереди (см. 7.3).

### 6.4. Последовательность

```
A                                   сервер                                   B
|-- JOIN(jwt) ------------------------>|                                      |
|<-- SYSTEM(Welcome) ------------------|                                      |
|-- GET_KEY(bob) --------------------->|                                      |
|<-- PUBLIC_KEY(bob, rsaB) ------------|                                      |
|-- INIT_SESSION(bob, E_A, sig_A) ---->|-- INIT_SESSION(alice, E_A, sig_A) -->|
|                                      |<-- SESSION_ACK(alice, E_B, sig_B, conf_B)
|<-- SESSION_ACK(bob, E_B, sig_B, conf_B)                                      |
|-- SESSION_CONFIRM(bob, conf_A) ----->|-- SESSION_CONFIRM(alice, conf_A) --->|
|-- SEND_MESSAGE(bob, ver=3, flag, E_A, seq=0, idx=0, ...) -->|
|                                      |              |-- DM(alice, ver=3, flag, E_A, seq=0, idx=0, ...) -->|
```

Шаги:

1. `A` получает `rsaB`, генерирует `(E_A, e_A)`, подписывает payload и шлёт
   `INIT_SESSION`.
2. `B` проверяет подпись `A` по `rsaA` (полученному через `GET_KEY`).
3. `B` генерирует `(E_B, e_B)`, считает `K`, `H` и `root`, подписывает
   `role="ack"`, вычисляет `conf_B`, отправляет `SESSION_ACK`.
4. `A` проверяет подпись `B`, считает `K`, `H` и `root`, сравнивает `conf_B`
   в постоянном времени. При успехе отправляет `SESSION_CONFIRM` с `conf_A`,
   затем помечает сессию `READY`.
5. `B` сравнивает `conf_A` в постоянном времени и только после этого помечает
   сессию `READY`.

Сессия не используется для сообщений до завершения подтверждения.
Эфемерные пары handshake **не уничтожаются** — они становятся начальной
парой ратчета (см. 6.3 и 7.3).

### 6.5. Одновременный handshake

Без изменений: сторону с лексикографически меньшим именем оставляем
инициатором, вторая сторона уничтожает pending-контекст и отвечает как
responder (`ChatClientCore.shouldAcceptIncomingHandshake`).

## 7. Формат E2E-сообщения (v3)

### 7.1. Кадр

`e2ePayload` — Base64 от:

```
+--------+-------+--------------------+-----------+-------------+-------+-----------------------------+
| ver(1) | flags | ratchetPub(65)?    | seq(8,BE) | chainIdx(8) | IV(12)| AES-256-GCM ciphertext+tag |
+--------+-------+--------------------+-----------+-------------+-------+-----------------------------+
```

- `ver = 3`.
- `flags` — бит 0 (`0x01`) = «в этом кадре свежий ratchet-ключ»; остальные
  биты зарезервированы и **должны быть нулями** (иначе кадр отклоняется).
- `ratchetPub` — сырой uncompressed point P-256 `0x04 || X(32) || Y(32)`,
  присутствует только при `flags & 0x01`.
- `seq` — глобальный счётчик направления, строго `+1`.
- `chainIndex` — позиция в текущей HMAC-цепочке; после ротации сбрасывается
  в `0`.

Минимальная длина кадра: `1+1+8+8+12+16 = 46` байт; с ratchet-ключом —
`46 + 65 = 111` байт.

### 7.2. AAD

```
AAD = ver(1) || flags(1) || len(ratchetPub)(4) || ratchetPub ||
      len(sender)(4) || sender || len(recipient)(4) || recipient ||
      seq(8, BE) || chainIndex(8, BE)
```

Всё содержимое заголовка аутентифицировано: нельзя тихо выкинуть флаг
ротации, подменить ratchet-ключ, переписать отправителя, sequence или
chainIndex.

### 7.3. Ключи сообщений и ротация

Симметричный рatchet (`SessionCrypto.kdfCk`), выполняется на **каждое**
сообщение:

```
messageKey_n = HMAC-SHA256(key = chain_n,     message = "secure-chat/v3/msg-key")
chain_{n+1}  = HMAC-SHA256(key = chain_n,     message = "secure-chat/v3/next-chain")
```

HMAC односторонний: зная `messageKey_n` или `chain_{n+1}`, предыдущие
значения не восстановить → прошлые сообщения закрыты навсегда.

DH-ротация (`SessionCrypto.kdfRk`, шаги из 6.3) выполняется **только когда
пришло сообщение со свежим ratchet-ключом собеседника** (`flags & 0x01`):

```
шаг 1: (root, recvChain) = kdfRk(root, DH(своя_текущая_пара, peerNewKey), dir = «входящее»)
шаг 2: своя_пара = новая пара P-256
       (root, sendChain) = kdfRk(root, DH(своя_новая_пара, peerNewKey), dir = «исходящее»)
```

Правила сходимости (обязательны для реализации):

1. **Ротация только по получению.** Сторона никогда не ротирует «сама» —
   только в ответ на свежий ключ собеседника. Поэтому последовательность
   KDF-шагов у обеих сторон совпадает, и корни/цепочки не расходятся.
   (Одновременная «самостоятельная» ротация обеих сторон сломала бы
   сходимость — проверено при проектировании.)
2. `dir` — направление цепочки (`i2r`/`r2i`), одинаковое у обеих сторон для
   одного и того же шага.
3. Первое сообщение каждого направления несёт `flags = 0x01`: у инициатора —
   начальный `E_A` (ленивая цепочка), у ответчика — `E_B2` (шаг 2 из 6.3).
   Последующие сообщения до следующей ротации — `flags = 0`.

### 7.4. Двухфазное обновление состояния

Отправка (`beginSend` → `commitSend`):

1. `beginSend`: если `sendChain` пуста — ленивый `kdfRk`; затем `kdfCk`,
   формируется **тикет** (sequence, chainIndex, messageKey, ratchetPub?,
   nextSendChain). Состояние не меняется.
2. Шифрование и запись в сеть.
3. `commitSend`: счётчики и цепочка продвигаются; messageKey затирается.

Приём (`planReceive` → `commitReceive`):

1. `planReceive`: проверка `seq == lastReceived + 1`; при `flags & 0x01` —
   проверка точки на кривой и **вычисление** шагов ратчета; проверка
   `chainIndex`; вычисление `messageKey`. Всё кладётся в **план**.
2. GCM-тег проверяется отдельно.
3. `commitReceive`: состояние меняется только после успешной проверки.

Следствие: подделанный/переигранный кадр отклоняется **до** изменения
состояния — атакующий не может сбить ратчет синхронизации.

### 7.5. Правила приёма

1. Длина ≥ 46 байт (или ≥ 111 при флаге) после Base64-декодирования.
2. `ver == 3`; неизвестные биты `flags` → отказ.
3. `seq == lastReceived + 1` (строго, без пропусков и переупорядочивания).
4. `chainIndex == (флаг ? 0 : текущий recvChainIndex)`.
5. При флаге: точка валидна и лежит на `secp256r1`.
6. GCM-тег совпадает.
7. Только после пунктов 3–6 состояние (счётчики, цепочки, корень, пара)
   обновляется, `lastReceived` увеличивается.

Отклонение любого пункта → кадр отбрасывается, состояние не меняется
(`DECRYPTION_FAILED` на стороне приёма).

Nonce и timestamp в `SEND_MESSAGE` — дополнительная грубая защита на уровне
сервера (кэш `(sender, nonce)` на 60 секунд, допуск часов ±30 секунд).

### 7.6. Порядок доставки

Протокол **требует строгого порядка** в направлении: пропущенный кадр
отклоняет последующие (цепочка рассинхронизируется по построению). Офлайн-
очереди нет; при рассинхронизации сессия переустанавливается новым
handshake. Это осознанное ограничение (см. `SECURITY.md`, §9).

## 8. Жизненный цикл сессии

- `WAITING_FOR_ACK` — инициатор отправил INIT.
- `WAITING_FOR_CONFIRM` — ответчик отправил ACK и ждёт CONFIRM.
- `READY` — ключи подтверждены, можно слать сообщения.
- `FAILED` — handshake отклонён или уничтожен.

Таймауты:

- idle — 30 минут без активности;
- absolute — 24 часа с момента создания.

При истечении сессия уничтожается вместе со всем ратчет-материалом
(корень, цепочки, пара), а следующее сообщение запускает новый handshake.
При отключении клиента все сессии уничтожаются.

Кадентность ротации: корень пересчитывается при каждой смене ratchet-ключа,
т.е. один раз за ход (сообщения одного направления подряд). Ключи сообщений
меняются при **каждом** сообщении.

Сервер (без изменений):

- idle-таймаут соединения — 30 минут;
- лимит команд — 60 за 10 секунд на соединение;
- пул потоков — 8–64 потока, очередь 256; при переполнении соединение
  отклоняется;
- одновременно разрешено одно соединение на username.

## 10. Свойства безопасности

Обеспечивается:

- конфиденциальность содержимого от сервера и сети (E2E + TLS);
- целостность и аутентичность сообщений (GCM + AAD на весь заголовок);
- **per-message forward secrecy** — утечка ключа одного сообщения не открывает
  ни прошлые, ни последующие;
- **break-in recovery** — DH-ротация пересчитывает корень каждый ход, украденное
  состояние перестаёт открывать сообщения после следующей ротации;
- защита от replay/переупорядочивания/пропусков (sequence + chainIndex +
  строгий порядок);
- аутентификация handshake долгоживущими RSA-ключами;
- привязка ключей к транскрипту и направлениям;
- защита от подмены имени в чате (имя берётся из JWT);
- локальное закрепление (TOFU) публичных ключей собеседников: последующая
  смена ключа сервером отклоняется до явного `/trust`;
- safety numbers, вычисляемые из обоих identity-ключей, для сверки по другому
  каналу (`/safety <user>`).

Не обеспечивается (см. [`SECURITY.md`](../../SECURITY.md)):

- защита от malicious-сервера при **первом** получении ключа: TOFU доверяет
  первому ключу, а сверка safety number выполняется вручную, а не принудительно;
- key transparency (append-only log), который позволил бы проверять ключи без
  ручного сравнения;
- хранение пропущенных ключей (skipped message keys) и работа при нарушении
  порядка — требуется строгий in-order;
- шифрование заголовка (сервер видит sequence и кадентность ротации);
- отзыв JWT и refresh-токены;
- сокрытие метаданных от сервера.

## 11. Константы

| Параметр | Значение |
|----------|----------|
| Версия E2E | `3` |
| Флаг ratchet-ключа | `0x01` |
| Ratchet-ключ в кадре | сырой point P-256, 65 байт (`0x04‖X‖Y`) |
| Кривая ECDH | `secp256r1` (P-256) |
| Identity | RSA ≥ 2048, `SHA256withRSA` |
| Симметричный шифр | AES-256-GCM, тег 128 бит |
| IV | 12 байт, случайный на сообщение |
| Цепочка | HMAC-SHA256: `msg-key`, `next-chain` |
| Ротация | DHKDF: `prk = HMAC(root, dh)`, `…/ratchet/<dir>/{root,chain}` |
| HKDF (handshake) | HMAC-SHA256, salt = SHA-256 транскрипта |
| Транскрипт / подписи | SHA-256 / `SHA256withRSA`, label `secure-chat/v3/…` |
| PBKDF2 | HMAC-SHA256, 600 000 итераций, соль 16 байт |
| Формат файла ключа | `SCK1` + salt + IV + ciphertext |
| Мин. длина кадра v3 | 46 байт (111 с ratchet-ключом) |
| Таймаут handshake на клиенте | 10 секунд |
| Idle-таймаут сессии | 30 минут |
| Absolute-таймаут сессии | 24 часа |
| Допуск timestamp | ±30 секунд |
| Максимальный кадр | 96 KiB |
